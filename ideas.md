## Lessons

Raw capture point for operator/agent lessons + gotchas. `/noldor-absorb` classifies each unfiled bullet (`drop | gotcha | actionable | feedback`), files it into framework docs, and stamps `[absorbed YYYY-MM-DD → <dest>]`. Stamped bullets may be pruned — git history is the audit trail.

- v1.10.0 release aborted on the `sdd-report` gate minutes after a fully green `--preflight`, because the report's **override-record list is filtered by a 30-day rolling window** and commit `5c35053` (2026-08-17) aged out of it mid-sweep. The sweep's step 5.5 / 6.5 pre-empts cannot outrun a clock: they re-run the regen at a point in time, and any later clock-derived line can re-drift before `pnpm release` reaches its own gate. The adjacent `Review-skip count` line is already masked by `VOLATILE_METRIC_IDS` (`src/garden/sdd-report-format.ts`), but the override-record bullets it sits under are not, so only the bullets block. Candidate fixes: (a) mask the override-record section the same way `onlyVolatileSectionsChanged` masks the metric blocks, since both are clock-derived rather than content-derived; or (b) have the release gate re-run the regen itself and auto-commit a diff that is *only* window-aging. Cost this time: one extra micro-chore PR (#469) + a second `pnpm release` run.
- A config-supplied git rev that is only **shape**-validated, feeding a `git log` whose caller wraps it in `catch { return []; }`, silently disables the check it scopes. Q-0242's `release.gateComplianceSince` shipped with a `/^[0-9a-f]{7,40}$/` schema regex; a one-character typo yields a rev git rejects, both gate-compliance detectors swallow the failure, and the release row goes permanently green — quieter than `RELEASE_SKIP_GATE_COMPLIANCE`, which at least logs to `.noldor/overrides.log`. Caught by the code-stage reviewer, fixed by resolving the floor with `git rev-parse --verify <sha>^{commit}` and discarding an unresolvable one with a warning. The general shape is worth a sweep: every `catch { return []; }` around a spawn whose arguments come from consumer config is a place where a typo buys silence instead of an error. Candidate: a lint or invariant over `src/**` that flags a swallowed-error spawn whose args include a config-sourced value.
- `pnpm release`'s npm-publish wait (290s) starts when the tag is pushed, but the publish workflow still has to queue and run, and npm then warns the package "may take a few minutes to become available". v1.10.0 published fine (`+ @david.zoufaly/noldor@1.10.0`, signed provenance, workflow green in 40s) yet the release still aborted on a registry-visibility timeout. `pnpm release --resume` finished it cleanly. Consider raising the wait, or starting the clock when the workflow reports success rather than at tag push.

- **`next-priority` ignores `blocked-by`, and nothing detects a blocker ordered *below* the entry it blocks.** Reproduced in a consumer: `Q-0243` carried `- blocked-by: Q-0255`, `Q-0255` sat one position lower in `docs/roadmap.md`, and `pnpm noldor next-priority` answered `Chat Panel UI Overhaul` while `pnpm noldor validate triage` reported `0 advisories`. Since file order is priority and `next-priority` is what `/noldor-gate` Step 0 picks up, the gate hands an agent an entry whose first act is impossible — here, a feature that deletes the product's only API-key entry point before its replacement exists. The dependency was expressed correctly; only the *order* was wrong, and nothing in the framework can see that. Candidates: (a) `next-priority` skips, or at minimum warns on, an entry whose `blocked-by` resolves to an unshipped entry; (b) a `validate:triage` detector for "blocker appears later in file order than its dependent" — cheap, because `parseRoadmap` already has both the order and the refs, and `/noldor-garden`'s `circular-blocked-by` already walks that same graph.
- **Milestone membership rots by omission, and there is no tooling to assign it.** `validate:triage` catches a *typo'd* slug well — injecting `pubic-relase-typo` produced 11 `unknown-milestone-ref` errors, and `lefthook/noldor.yml` runs the check on every `docs/{roadmap,backlog}.md` commit — but nothing notices an entry carrying **no** `milestone:` at all. In a consumer mid-milestone, 50 of 54 roadmap entries had none, so `milestones show <active>` listed 4 queued items and the active milestone could not answer how far through it was. The only related command, `features attach-milestone`, is a *verdict* (entry vs parent FD) rather than a tagger, so the fix is hand-editing N blocks. Candidates: a `milestones assign <slug> <entry…>`, and an unassigned-entry count surfaced by `milestones show` or the sdd-report, so the gap is visible without a bespoke script.
- **`Features (n/n done)` is structurally always `0/0`, because nothing writes a milestone onto a feature MD.** `milestones show` renders the section and the schema supports it, but no FD in the consumer carried the field, no command sets it, and `/noldor-milestone` only manages the milestone *files*. Milestone progress is therefore unmeasurable for every milestone including the active one — the one number an operator actually wants from `milestones show`. Candidate: have the gate stamp the milestone onto the FD at attach time (`attach-milestone` already computes the verdict, so it knows the value), and let `phase-flip-done` be what moves the `n/n` counter.
- **`blocked-by` is all-or-nothing, so a partial dependency degrades into prose the scorer cannot see.** Several entries in this consumer can start and two-thirds ship while one part waits: a bar whose five sections are independently blocked, a panel where one row needs a concept that does not exist yet. Marking the whole entry `blocked-by` divides its score by `1 + unshipped_dep_count` for work that is mostly doable today; leaving it off loses the dependency from the graph entirely, so `/noldor-garden` cannot see it and a reader has to find it in a paragraph. Candidate: a `partially-blocked-by:` that joins the blocked-by graph for cycle detection and `show` output but is excluded from the dependency factor — the semantics being "cannot finish" rather than "cannot start".
- **Milestones have no order, so `milestones show` and the dashboard sort drafts alphabetically and paint the ladder wrong.** `buildMilestoneGroupBases` (`src/milestones/lib.ts:341`) orders by status then `name.localeCompare`, and the frontmatter schema carries only `name` / `status` / `description`. In a consumer with four drafts the list read `community, energy-addon, garden-addon, public-release` — two paid post-GA addons rendered *above* the GA milestone whose `## Out of Scope` explicitly defers them, and the only place the real sequence lives is prose ("Milestone 2 — it follows `real-materials`"). Candidates: an optional `after: <slug>` (or `order: n`) in milestone frontmatter, honoured by `show`, the `/milestones` page and `milestones validate` (unknown slug, cycle, two milestones claiming the same predecessor); `/noldor-milestone draft` asks for it. Pairs with the two milestone-membership bullets above — assignment says *what* belongs to a milestone, this says *when* the milestone comes.

- **The verify lane cannot report on a change whose evidence contains fenced code, because its own payload is a fence.** Shipping Q-0239 (PR #478) the verifier ran the whole acceptance set twice — against a scratch consumer and against real charuy — and emitted `{"verdict":"pass"}` both times, but `parseVerifyPayload` recovered neither: the evidence strings quote the fenced ` ```bash ` blocks the change is *about*, so the inner backticks closed the outer fence early. The repair round failed the same way, for the same reason, and the `proseReportsSuccess` valve (`src/cr/lanes/verify.ts:72`) missed too, because the prose opened "Done. Everything the change promised works when I actually ran it" — no `verifi*` stem — so `PROSE_SUCCESS_RE` never matched and the round fell to the fail-closed `high` blocker. Net: a green verification blocked a ship on a serialization defect, and the only exit was `Noldor-Path-Override`. This is systematic, not flaky — any change to fence handling, markdown parsing or skill bodies reproduces it. Candidates: have the verifier emit its payload on a `~~~`-delimited fence (the parser already accepts `~~~` for skills), or length-prefix / base64 the evidence, or teach the extractor to take the LAST balanced fence rather than the first close. Pairs with Q-0137, which built the repair round for the same class and is now shown to under-reach.
- **`proseReportsSuccess` requires a word the verifier has no reason to use.** `PROSE_SUCCESS_RE` wants a `verifi*` stem or "all checks pass"; a verifier writing plainly ("Everything the change promised works when I actually ran it", "Nothing is left running") matches nothing, while `PROSE_FAILURE_RE` vetoes on `\bmissing\b` / `\bwrong\b` / `\bcannot\b` — words that appear constantly in an honest *description of what was tested*, e.g. "adding a made-up script gives the wrong-script message". So the valve is biased hard toward veto in exactly the rounds it exists to rescue. Candidate: stop pattern-matching free prose and make the lane prompt demand a one-line machine verdict on its own line outside any fence (`NOLDOR-VERDICT: pass`), which survives every fence-nesting failure above.
- **Q-0231 "show-more not rendered" was PR #476's zombie seen from the browser, and the UI was fail-closed to it.** The stale-install dashboard rendered pages from memory while `/static/drag.js` 500'd, so the inline CSS clamped every description to six lines and the JS that reveals the Show more control never ran. Headless Chromium 151/153 and WebKit 26.5 against charuy's restarted 1.10.0 dashboard showed 45/45 controls — the entry no longer reproduced once the process was replaced. PR #482 made the clamp opt-in (drag.js adds `js-clamp` per cell; CSS rests on the full body), so a missing script can no longer trap content. Gotcha for triage: an entry reporting a *JS-revealed control missing on a consumer* should first check whether that consumer's dashboard process predates its noldor install (`ps -o lstart= -p $(lsof -ti :<port>)` vs the install date) before anyone debugs CSS. (found 2026-09-19 shipping Q-0231)
- **`src/dashboard/layout.ts` `STYLE` is a JS template literal, so a backtick anywhere in a CSS comment ends the string.** oxlint reports it as `Expected a semicolon or an implicit semicolon` at the backtick's column and every dashboard test file fails to import — neither message says "template literal". Write class names in CSS comments bare. (found 2026-09-19 shipping Q-0231)
- **`src/dashboard/static/dist/*.js` are tracked build artifacts that nothing in `bin/build.mjs` regenerates and no test checks against their `.ts` source.** The recipe that reproduces the tracked bytes exactly is `node_modules/.bin/tsc -p src/dashboard/static/tsconfig.json` followed by `node_modules/.bin/oxfmt src/dashboard/static/dist/drag.js src/dashboard/static/dist/agents.js` (tsc alone emits 4-space output and diffs everywhere). A browser-side change that skips the second step lands a 400-line whitespace diff; one that skips both ships stale JS while the `.ts` reads fixed. Wanted: a test or pre-commit job that compiles the two sources to a temp dir and diffs them against the tracked dist. (found 2026-09-19 shipping Q-0231)
- **Browser-level verification of a dashboard change is doable headless from a drain child.** noldor has no playwright, but `/Users/davidzoufaly/code/charuy/node_modules/playwright` does; the probe script must sit under a `node_modules/.cache/` dir (or import by absolute path) for resolution to work, `PORT=<n> pnpm noldor dashboard server` run from the worktree serves that worktree's `src/`, and `page.route('**/static/drag.js', r => r.abort())` reproduces the zombie's missing script in one line. `chromium.launch({ channel: 'chrome' })` drives the operator's real installed Chrome. (found 2026-09-19 shipping Q-0231)
- **A background `git commit -F <file>` exited 1 with zero output once, and the identical retry passed with the full lefthook summary.** Check `git log` and `git status` before debugging a silent commit failure — the files stayed staged, nothing was lost, and `pnpm exec lefthook run pre-commit` by hand was green in between. Unknown cause; two data points would make it a gotcha entry. (found 2026-09-19 shipping Q-0231)
- **A reviewer lane that writes `- (none)` under an empty severity bucket reds the round with phantom blockers, and nothing downstream can tell them from real ones.** Shipping Q-0246 the code-stage reviewer returned `summary: "approve"` with a single Strengths note, yet its sink carried `[high]` and `[med]` blockers plus a `[low]` suggestion whose `message` was the literal string `(none)`; `cr aggregate` read `ok=false` and exited 1, and no `Noldor-Reviewed-Subagent` receipt was minted, so the push would have been refused on a review that had approved. `cr autofix plan` declined `no-mechanical` and routed both to the operator as `D1`/`D2` — there is nothing to apply, the messages are empty. The lane prompt in `src/cr/lanes/subagent-dispatch.ts:191` does say "Leave a bucket's bullet list empty (no bullets) when there are no items at that severity", so this is a model formatting slip the parser has no guard against; an identical re-dispatch over the same tree came back with `blockers: []` and went green, which also confirms it is non-deterministic rather than a property of the diff. Two independent holes worth closing: the extractor should drop a bullet whose text is empty or `(none)` (case-insensitive, parens optional), and the aggregate's `ok` should not be able to disagree with a lane's own `approve` summary without saying so. Pairs with the verify-lane fence blindspot below — same class: a lane's serialization defect blocking a ship its content approved. (found 2026-09-20 shipping Q-0246)
- **`pnpm noldor cr aggregate` exits non-zero, so piping it to `tail` in the zsh Bash tool silently reports success.** `cr aggregate ... | tail -20` then `echo $?` prints `tail`'s status, not aggregate's — during Q-0246 that turned a genuine red round (exit 1) into an apparent `AGG_EXIT:0` sitting directly under the text `ok=false`. `PIPESTATUS` is empty in this shell (see the existing env memory), so the only reliable shape for any exit-code-bearing noldor command is redirect-then-cat: `cmd > /tmp/out 2>&1; echo "EXIT:$?"; cat /tmp/out`. Worth stating in the gate prose wherever it tells the controller to "capture stdout + exit code". (found 2026-09-20 shipping Q-0246)
