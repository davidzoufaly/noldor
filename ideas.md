Root cause is that `<!-- ... ```mermaid ... a --> b ... ``` ... -->` closes at the mermaid ARROW, because a flowchart edge *is* `-->`. - zsh does not word-split unquoted parameter expansions, and the CLI's not-found message actively misleads when you hit it. A loop of the shape `for cmd in "sync code-links" "sync test-links"; do pnpm noldor $cmd; done` passes ONE argument (`"sync code-links"`) rather than two, so every command returns `Unknown command: sync code-links` — followed by the framework's helpful skew hint ("your repo is anchored at framework (unset) but 1.6.0 is installed... run 'noldor upgrade' then 'noldor init --update'"), which sends you chasing a version-skew ghost instead of a quoting bug. Compounded by the already-known trap that a pipe eats the exit code: `pnpm noldor $cmd 2>&1 | tail -6` returns tail's status, so `set -e` did not fire and the loop printed a success marker after every failure. Use a wrapper that preserves argv and status: `run() { pnpm --silent noldor "$@" > /tmp/o.txt 2>&1; local e=$?; tail -6 /tmp/o.txt; return $e; }`. Worth noting the skew hint fires on *any* unknown command, including a typo, so it should probably only appear when the anchor genuinely differs from the installed version rather than when it is merely unset. (found 2026-09-03, v1.7.0 release sweep)

- A roadmap entry's stated root cause can be a strict subset of the real one, and a *green test* can be the thing holding the bug in place. Q-0207 blamed "the last rung of the ladder" — `resolveRoot` falling back to the artifact's own checkout. That rung was guilty, but so was rung 2: the hook feeds `payload.cwd` into the soft workspace-root rung, and in a `specs-only-*` / `full-*` session that cwd **is** the worktree, so rung 2 contained the artifact and answered with the very root the fallback would have. Fixing only the named rung would have left the link dead whenever a hint arrived — i.e. whenever the hook is the caller, which is every Claude session. Worse, `src/hooks/__tests__/noldor-open-artifact.test.ts` asserted the bare path for `cwd: tree` under the comment "the inverse layout: the operator opened the worktree as its own window" — treating the *agent's* cwd as evidence about the *editor's* window, and pinning the defect as intended behaviour. The generalisable rule: when an entry names one code path, enumerate the other callers of the same decision before implementing, and read any test asserting current behaviour as a claim to re-argue rather than a constraint to preserve. - A `noldor:cut` marker can launder a defect as a decision, and the CR is what catches it. The first Q-0207 implementation cut at "the standard `<root>/.git` layout" and claimed the two existing guards made a wrong derivation *inert rather than wrong*. The reviewer falsified that in one round: a bare repo (`/proj/repo.git` with sibling worktrees `/proj/a`, `/proj/b`) has no main checkout at all, yet `dirname('/proj/repo.git')` is `/proj`, which both exists **and** contains the artifact — so both guards pass and the steer prints `a/docs/design/specs/…` against a root nobody opened. - `git rev-parse` mixes relative and absolute answers within a single invocation, which silently breaks any string comparison between two of its path flags. From a subdirectory of a main checkout, `--git-common-dir` answers relative (`../../../.git`) while `--git-dir` answers absolute — so `commonDir !== gitDir`, the obvious linked-worktree test, reads the *primary* case as a worktree. Both must be `resolve()`d against the probe's cwd before comparing. This is not a corner case for `src/design/open-artifact.ts`: `classify` probes from the artifact's parent directory, never the repo root, so the subdirectory shape is the only shape it ever sees. Also recorded from the same change: widening one `rev-parse` from one flag to three (`--show-toplevel --git-common-dir --git-dir`) keeps the module's documented single-probe latency bound intact — the extra questions ride the existing `execFileSync`, output line order follows flag order, and treating the trailing lines as optional lets an odd git degrade to the prior behaviour instead of to a rejection. Worth a house note wherever git probes are composed. (found 2026-09-03, Q-0207 fast-track)
