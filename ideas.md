Raw capture point for operator/agent lessons + gotchas. `/noldor-absorb` classifies each unfiled bullet (`drop | gotcha | actionable | feedback`), files it into framework docs, and stamps `[absorbed YYYY-MM-DD → <dest>]`. Stamped bullets may be pruned — git history is the audit trail.

- `toolchain-floor` reads root tsconfigs only (`TSCONFIG_CANDIDATES` = `tsconfig.base.json`, `tsconfig.json`), so a nested config below the lib floor passes unseen. Found live: `src/dashboard/static/tsconfig.json` sat at `lib: ["ES2023", "DOM"]` while `platform-over-dependency` and `deterministic-cleanup` both bind `**/*.ts` — which includes `drag.ts` and `agents.ts` — and mandate `Set.prototype.union` and `Symbol.dispose`, each a TS2550 under that lib. The `lib-inherited` guard cannot help: it stays quiet because the *root* config declares a `lib`, and it is decided repo-wide by design. So two enforced rules mandated code a real config in this repo rejects, and nothing reported it. Options: walk every tsconfig the workspace scan already finds (the manifest walk is right there), or assert that a nested config either declares no `lib` — inheriting the base — or meets the floor itself. Worth noting `lib` REPLACES rather than merges on `extends`, so putting the floor in a base config protects only children that omit `lib` entirely. (found 2026-08-26, CR on the tsconfig-shared-base refactor) [absorbed 2026-09-02 → ideas]

- A markdown scanner that blanks HTML comments must interleave comment state with fence state in ONE pass, and the interaction is nastier than it looks. Three consecutive attempts each shipped a distinct hole on the `fd-diagram` detector (Q-0185): (1) blanking only inside a located section let a `## Diagram` inside a comment *enrol* an FD that predated the contract, breaking a presence-gating guarantee outright; (2) blanking the whole body before locating fixed that but treated `<!--` inside a fenced example as a real comment, so an unterminated one blanked the rest of the file and the FD silently left scope; (3) making the blanker fence-aware fixed that but exposed a worse one — a commented-out mermaid fence blanks its *opening* delimiter (it sits inside the comment) while the *closing* ```` ``` ```` survives past the `-->`, and `tagLines` reads that stray delimiter as an opener, so every heading to EOF vanishes. `locateSection('## Usage')` → `null`; the whole FD returns `[]`. Root cause is that `<!-- ... ```mermaid ... a --> b ... ``` ... -->` closes at the mermaid ARROW, because a flowchart edge *is* `-->`. Two candidate fixes named at review: keep blanking through a fence that was opened inside a comment, or make `tagLines` ignore an unmatched closer. Worth noting the CommonMark fence grammar ended up implemented twice in one file (`tagLines` and `blankComments`) and the two copies already disagreed on a rejected backtick opener — the exact fork the module docstring existed to prevent. Deletion test: an FD quoting this framework's own `## Diagram` scaffold inside a fenced sample is still scanned. (found 2026-08-29, three CR rounds on Q-0185) [absorbed 2026-09-02 → gotchas]

A one-space-indented `## Usage` therefore fails to close the preceding section and its prose is measured as the previous section's. One `atxHeading(line)` helper at all three sites. So the report re-drifts *after* the step whose entire purpose is to pre-empt it. Confirmed live on the v1.7.0 sweep: step 5.5 committed a regen, the garden pass committed the spec archive plus 18 FD resource updates, and `pnpm release --preflight` then came back `FAIL sdd-report — regenerated report differs from the committed copy`. This is not maskable — the drift is in gap details, not the volatile sections `onlyVolatileSectionsChanged` filters — and because direct push to `origin/main` is blocked, the fix costs a whole extra branch + PR after the sweep PR has already merged. Fix is pure ordering: move the sdd-report regen so it runs after the garden pass, or fold it into the garden regen chain itself (it is already the last thing that can change gap rows). Note the same trap catches `graphify-out/` only by luck — graph freshness scans `scanRoots()`, which is source dirs, so doc commits do not stale it. Deletion test: a sweep that archives a spec and re-runs `sync code-links` reaches `--preflight` with `sdd-report` green and no follow-up commit. (found 2026-09-03, v1.7.0 release sweep)

- Garden's stale-spec/stale-plan detectors report 0 on artifacts they structurally cannot see, and only the skill's *manual sweep* step catches them. On the v1.7.0 sweep `staleSpecs` was 0 while all 12 live specs under `docs/design/specs/` belonged to features that were already `phase: done` — oldest dated 2026-06-07, roughly three months stale. Cause is the filename shape: these are named `<parent-feature-slug>-<sub-scope>-design.md` (e.g. `de-superpowers-vendor-spec-plan-and-worktree-flows-decision-context-depth-design`), and the detector resolves an owner by stripping the date prefix and `-design` suffix then looking up that whole remainder as a feature slug — which misses, so the artifact is treated as ownerless rather than as belonging to a done parent. The `/noldor-garden` skill already documents this ("Multi-feature plans, infra plans, and parent-plus-`-partN` splits all slip through when their slug doesn't match a feature MD") and prescribes the manual sweep, so the workaround exists — but a detector that returns 0 reads as "nothing to do" and the manual step is easy to skip under a green number. Fix: fall back to longest-prefix matching against known feature slugs when the exact lookup misses, which is exactly what the manual sweep does by hand. Deletion test: a spec named `<done-feature-slug>-<suffix>-design.md` appears in `staleSpecs`. (found 2026-09-03, v1.7.0 release sweep)

- zsh does not word-split unquoted parameter expansions, and the CLI's not-found message actively misleads when you hit it. A loop of the shape `for cmd in "sync code-links" "sync test-links"; do pnpm noldor $cmd; done` passes ONE argument (`"sync code-links"`) rather than two, so every command returns `Unknown command: sync code-links` — followed by the framework's helpful skew hint ("your repo is anchored at framework (unset) but 1.6.0 is installed... run 'noldor upgrade' then 'noldor init --update'"), which sends you chasing a version-skew ghost instead of a quoting bug. Compounded by the already-known trap that a pipe eats the exit code: `pnpm noldor $cmd 2>&1 | tail -6` returns tail's status, so `set -e` did not fire and the loop printed a success marker after every failure. Use a wrapper that preserves argv and status: `run() { pnpm --silent noldor "$@" > /tmp/o.txt 2>&1; local e=$?; tail -6 /tmp/o.txt; return $e; }`. Worth noting the skew hint fires on *any* unknown command, including a typo, so it should probably only appear when the anchor genuinely differs from the installed version rather than when it is merely unset. (found 2026-09-03, v1.7.0 release sweep)
