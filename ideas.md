## Not groomed

- Extract the shared tsconfig reader into a neutral module. `src/invariants/toolchain-floor.ts` and `src/indirection/detect.ts` each carry their own tsconfig discovery — `findPackageManifests`/`isTsconfigName` on one side, `findTsconfigFiles`/`readTsconfig`/`resolveExtends` on the other — and `detect.ts` already imports `stripJsonc` from `toolchain-floor.ts`, so importing discovery back would close a module cycle. PR #436 duplicated it deliberately and promised this entry in the spec's Risks section. The two walks are not a clean lift (async `readdir` + `WORKSPACE_SCAN_DEPTH` here, sync `readdirSync` + configured scan roots there), so the shared helper has to be designed rather than moved, and it touches the indirection ratchet. `clones check` was green on #436, so this is cohesion debt rather than a live gate failure. Deletion test: both modules import their tsconfig discovery from one place, and neither declares a private copy. (surfaced 2026-09-05, spec CR on nested-tsconfig-lib-floor)

## Lessons

Raw capture point for operator/agent lessons + gotchas. `/noldor-absorb` classifies each unfiled bullet (`drop | gotcha | actionable | feedback`), files it into framework docs, and stamps `[absorbed YYYY-MM-DD → <dest>]`. Stamped bullets may be pruned — git history is the audit trail.

- **CR round cap: the sink goes stale once the cap refuses.** On Q-0083 (PR #437) `cr orchestrate` exited 3 at the cap without dispatching, so `cr aggregate` re-read the *previous* round's sink and reported 3 blockers of which 2 were already fixed in a later commit. The arbitration skeleton `orchestrate` writes is built from those same stale findings, so the operator writes dispositions against a list that no longer matches the tree — I had to hand-verify each blocker against the code before disposing of it. Either the skeleton should re-resolve each blocker's claim against `HEAD` before writing, or `aggregate` should refuse to report a sink whose `baseSha` is behind `HEAD` rather than printing it as current. (found 2026-09-06) [absorbed 2026-09-06 → ideas]

- **CR round ledger records `0 applied, 0 deferred` on every round `orchestrate` writes itself.** Same session: round 1 at code stage had 4 fixes applied, but the ledger shows all four rounds as `0 applied, 0 deferred`. Cause: `cr autofix record --applied 4 --deferred 1` refused with `--deferred 1 disagrees with the sinks: 5 design + 0 unapplied mechanical = 5` and exited non-zero, after which `orchestrate` recorded the round itself with zeros. The strict count check has no escape hatch for "I applied some of the design blockers by hand too", which is the normal shape of an operator round — so the accounting the cap reports back to the operator is silently wrong. Either accept `--deferred` below the sink count when `--applied` covers the difference, or count applied design blockers as applied. (found 2026-09-06) [absorbed 2026-09-06 → ideas]

- **Oscillation detector R3 is pure noise on a greenfield feature.** Nine R3 signals on PR #437, every one of the form "blocker at `<file>:<line>` is about line N, which this series introduced". On a feature that adds new files, *every* line is one the series introduced, so R3 fires on every finding and distinguishes nothing. Worth gating R3 on the file having existed before the series, or on the line having been touched by a *prior round in the same series* rather than by the series as a whole. (found 2026-09-06) [absorbed 2026-09-06 → ideas]

- **`/noldor-release-sweep` still encodes the step order that cost PR #422.** The v1.7.0 → v1.8.0 lesson was "run the garden pass BEFORE `garden sdd-report --release`, because the garden regen chain dirties `docs/features/**` and re-drifts the report" — but the skill file was never reordered: step 5.5 is the sdd-report pre-empt and step 6.5 is the garden pass. A controller following the skill literally does it backwards. On v1.9.0 it did not bite (the garden pass produced no sdd-report delta, so the re-run after it was a no-op), which is exactly why it will keep surviving reviews. Either swap 5.5 and 6.5 in the skill, or make 5.5 prose say "re-run after the garden pass and commit any further drift". (found 2026-09-06 releasing v1.9.0) [absorbed 2026-09-07 → ideas]

- **Q-0167's attach-flow blind spot is real, and `planWithoutFd` is the half that already catches it.** v1.9.0's garden pass reported `stalePlans: 0` and `staleSpecs: 0` while six live artifacts sat in `docs/design/` — five plan parts plus one spec for `cr-re-round-cap-enforcement-and-oscillation-detector-oscillation-detector`, whose parent FD went `phase: done` in PR #435. The plans were not invisible: `planWithoutFd` flagged all five with `reason: no-matching-fd`, because the `<parent>-<enhancement>` filename slug resolves to no FD. Only the **spec** was invisible to every detector — there is no `specWithoutFd` twin. So Q-0167 may be cheaper than its entry assumes: mirror `planWithoutFd` for specs rather than teaching `staleSpecs` about parent-slug derivation. (found 2026-09-06 releasing v1.9.0) [absorbed 2026-09-07 → drop]

- **The clean-preflight recipe is two by-hand steps, and neither is in the skill.** `pnpm release --preflight` came back 16-ok / 0-blocking on the first try for v1.9.0 only because I stamped `pnpm noldor garden receipt` by hand after the last HEAD-moving commit and cleared `.noldor/session.json` before running it. The skill's step 9 says to clear the mechanical rows with `--preflight --fix`, which cannot stamp the receipt in this repo (it needs zero `garden detect` findings; the repo permanently has ~190), and step 10 clears the session marker *after* step 9, so a literal reading always hits a red `session-marker` row first. Fold both into step 9's preamble. (found 2026-09-06 releasing v1.9.0) [absorbed 2026-09-07 → ideas]

- **zsh: an unquoted `--include=*.ts` aborts the command before it runs.** `grep -rn foo src --include=*.ts` dies with `zsh: no matches found: --include=*.ts` — zsh globs the flag's value against the *cwd* and fails the whole line when nothing matches, so the grep never executes and the failure reads like a broken search rather than a quoting bug. Always `--include='*.ts'`. Same class as the `$var` word-splitting trap from the v1.7.0 sweep. (found 2026-09-06 releasing v1.9.0) [absorbed 2026-09-07 → gotchas]

- **The heading slugifier DELETES non-ASCII letters rather than transliterating them, and `remove-block --split-into` cannot detect the mismatch.** Splitting Q-0193 (PR #448) I wrote a sibling heading containing `Façades`; the derived slug came out `...-faades-...`, not `...-facades-...`. The cost was not the ugly slug — it was that I had already passed my *guessed* slug to `roadmap remove-block --split-into`, which accepts any string and records it verbatim in `.noldor/retired-entry-ids.json`, so the retired-ID map pointed at a slug no entry had. `split-check --entry <guess>` is what caught it (`no roadmap/backlog entry with slug`), by accident. Two candidate fixes: transliterate in the slugifier (`ç → c`, `é → e`) so a heading a human would write round-trips, and have `--split-into` verify each named slug resolves to a block that now exists — it is called immediately after the siblings are written, so the check is free and a typo'd slug is otherwise invisible until a `blocked-by:` ref dangles. Deletion test: a heading with a non-ASCII letter yields a slug containing its ASCII fold, and `--split-into` with an unresolvable slug exits non-zero. (found 2026-09-07 splitting Q-0193) [absorbed 2026-09-07 → ideas]

- **`/noldor-gate`'s micro-chore step never says to check out the temp branch, and `pr-flow` reads `HEAD`.** Step 2's handoff recipe ends at `git stash pop` on rewound `main`, then hands off to "Step 4 end-of-flow takes over: `pr-flow.ts openAndAutoMerge()` pushes the temp branch" — which reads as though pr-flow resolves the branch from the session marker. It does not: `pr-flow-cli.ts:411` derives the branch from `git rev-parse --abbrev-ref HEAD` and exits at line 437 with `no commits ahead of origin/main on current branch` when run from `main`. A controller following the prose literally gets that error with a committed, pushed-nowhere temp branch and no obvious next move. Add the `git checkout <temp-branch>` as an explicit step 5.5 in the micro-chore recipe (and note that the popped dirty files travel along harmlessly). Same class as the drain-mode finish-vs-rebuild gap — knowledge that lived only in the caller. (found 2026-09-07 splitting Q-0193) [absorbed 2026-09-07 → ideas]

- **18 stale `origin/micro/*` branches, one per micro-chore PR ever shipped.** `pr-flow` deletes the *local* temp branch after the direct squash-merge but never the remote one, so every micro-chore since PR #318-ish has left a `origin/micro/<epoch>` behind (`origin/micro/changelog-node24-breaking` among them, so the leak predates the epoch naming). Harmless but it makes `git branch -r` unreadable and any branch-shaped audit noisy. Worth a `git push origin --delete <branch>` in pr-flow's post-merge cleanup, guarded on the merge having actually happened, plus a one-off sweep of the existing 18. (found 2026-09-07 splitting Q-0193) [absorbed 2026-09-07 → ideas]

- **A field added to a tracked state-file schema must be `.optional()`, or every existing file goes `unreadable` on upgrade.** Shipping Q-0213 added `perFile` to `cloneBaselineSchema`, which is `.strict()` and read by `clones check` on every push. A required field would have turned every consumer's committed `.noldor/clones-baseline.json` into `kind: 'unreadable'` — exit 3, ratchet off, across every repo, to gain a reporting nicety. Optional + a "predates attribution, re-record" message costs one branch and keeps the gate alive. Generalize: `.noldor/*.json` files are tracked and travel across framework versions, so their schemas are a compatibility surface, not an internal shape — the same rule the retired-ID map and the CR sinks live under, but nothing states it anywhere. Worth a rule (`state-file-schema-additive`) alongside the existing state-file rules. (found 2026-09-07 shipping Q-0213)

- **Fresh data point for Q-0214: a comments-and-one-field change to three sibling object literals moved the clone ratchet by -126.** Q-0213 touched only `detect.ts` / `baseline.ts` / `clones-cli.ts` and added no copied logic, yet whole-corpus `duplicatedTokens` fell 28967 -> 28841 and the group count 290 -> 289 — because adding `compared: false` to three neighbouring `return {...}` literals in `ratchetOutcome` changed how they structurally match. The ratchet moving on a change that provably added no duplication (in the *helpful* direction this time, which is why it went unnoticed) is the same sensitivity that forced two hand re-records; it is not only test scaffolds and import runs. Attach to Q-0214's evidence. (found 2026-09-07 shipping Q-0213)

- **R3's window still includes the first round's own commit, so a first round can fire with no prior round to oscillate against.** Shipping Q-0212 (PR #447) surfaced this next door: `resolveIntroducedLines` diffs `firstHeadSha^..HEAD`, and on an empty ledger `firstHeadSha` falls back to *this* round's head — so the range is `HEAD^..HEAD`, the last commit, not the empty range the call-site comment claimed (comment corrected in #447). Q-0212's pre-existence filter hides this for greenfield series, but on a series that EDITS existing code round 1 still gets R3 signals about lines its own pre-review commit added, and "the series introduced it" is not oscillation when nothing has been reviewed yet. The entry's second candidate fix — narrow the window to the rounds actually recorded in the ledger — is what closes it: drop the `^` so the window is `firstHeadSha..HEAD` (lines added *after* the first reviewed head), which is exactly "a prior round touched this line". Deletion test: a first CR round on an edit-only series emits zero R3 signals. (surfaced 2026-09-07) [triaged 2026-09-07 → r3s-window-includes-the-first-rounds-own-commit]
